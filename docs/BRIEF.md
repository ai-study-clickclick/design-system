# BRIEF.md

> 상태: 초안 v0.1 · 태스크: 1-6

화면 요청서(브리프)를 만드는 규칙이다

사람이 "로그인 화면 만들어줘"라고 말하면 Claude는 이 규칙대로 브리프 파일을 만든다. 화면은 그 브리프를 보고 만든다

이 문서는 "무엇을 만들지"만 정한다. 나머지는 아래 문서를 따른다

| 무엇 | 따르는 문서 |
| --- | --- |
| 색·크기·라운드 같은 디자인 값 | `DESIGN.md` |
| 화면 동작 | `docs/UX.md` |
| 문구 | `docs/WRITING.md` |
| 화면 유형별 구성 | `docs/PATTERNS.md` |
| 규칙 표시·문서 형식 | `docs/CONVENTIONS.md` "MD 작성" |

---

## 0. 브리프가 쓰이는 순서

```plain text
사람: "○○ 화면 만들어줘"
  → /brief            요청을 브리프 파일로 정리한다
  → /generate-screen  브리프를 보고 구성 계획을 세우고, 사람이 확인하면 화면을 만든다
  → /theme (선택)      테마를 바꿔 본다
  → /ui-review        만든 화면을 점검한다
```

- 순서의 기준은 `AGENTS.md` "스킬"이다
- 사람은 명령어를 몰라도 된다. "화면 만들어줘"라고만 해도 이 순서로 시작한다
- `/brief`는 보통 `/generate-screen`이 시작할 때 자동으로 부른다

## 1. 브리프 파일

| 항목 | 규칙 |
| --- | --- |
| 위치 | `briefs/` 폴더 |
| 파일 이름 | `YYMMDD-topic.md` (예: `261021-login.md`). 이름 규칙은 `docs/CONVENTIONS.md` "공통 이름 규칙"·"코드·피그마"를 따른다 |
| 화면 1개 | 브리프 1개 = 화면 1개 = 프로토타입 링크 1개 |
| 화면 주인 | `owner`에 적힌 사람이다 (`AGENTS.md` "역할과 작업 범위") |

Claude가 묻지 않고 알아서 채우는 칸이다

| 키 | 값 |
| --- | --- |
| `owner` | 지금 작업하는 사람의 Git 사용자 이름 (`git config user.name`) |
| `platform` | 늘 `app` |
| `output` | 늘 `prototype+figma` (10장) |
| `strict` | 보통 `false`. 결제·약관처럼 '~합니다' 말투가 필요한 엄격한 화면이면 `true` (`AGENTS.md` "확정된 기준"의 화면 문구 말투) |
| `level` | 4장 기준으로 나눈 결과. 쉬운 화면이면 `easy`, 어려운 화면이면 `hard`. "알아서 해줘"처럼 묻는 방식이 바뀌어도 그대로 둔다 |

- `owner`에는 Git 사용자 이름을 그대로 쓴다. Git 사용자 이름에 성이 들어 있으면 브리프를 만들지 않고 멈춘다. 성을 뺀 이름으로 바꿔 달라고 사람에게 알린다. 저장소가 공개라서다 (`AGENTS.md` "확정된 기준")
- 실제 사람의 이름·이메일·전화번호를 넣지 않는다. 예시 데이터는 지어낸 값만 쓴다
- 색·간격·라운드 같은 디자인 값은 적지 않는다. 값은 `DESIGN.md`가 정한다
- 화면이 여러 개 섞인 요청은 화면마다 브리프를 나눈다 (`docs/UX.md` "정보 구조")
- 사람이 처음 한 말은 "요청 원문"(`request`)에 고치거나 줄이지 않고 그대로 적는다. 브리프가 무엇에서 시작했는지 나중에 확인하기 위해서다 (`docs/CONVENTIONS.md` "MD 작성")
- 단, 요청 원문에 실제 사람의 이름·이메일·전화번호가 있으면 그 부분만 `[개인정보]`로 바꾼다. 저장소가 공개라서다

## 2. 꼭 채울 항목 6개

6개가 다 채워져야 화면을 만들기 시작한다. 항목은 `AGENTS.md` "스킬"을 따른다

| 항목 | 키 | 무엇을 적나 | 예시 (로그인 화면) |
| --- | --- | --- | --- |
| 목적·시나리오 | `goal` | 누가, 어떤 상황에서, 무엇을 하려고 이 화면에 오나 | 처음 앱을 연 사용자가 기존 계정으로 들어간다 |
| 플랫폼 | `platform` | 늘 앱(모바일). 묻지 않는다 | `app` |
| 범위 | `scope` | 이번에 만들 화면과 상태. 만들지 않는 것도 적는다 | 로그인 화면의 정상·오류 상태. 회원가입은 만들지 않는다 |
| 핵심 콘텐츠 | `content` | 화면에 꼭 보여야 하는 정보 | 이메일 입력, 비밀번호 입력, 비밀번호 찾기 링크 |
| 주요 액션 | `actions` | 사용자가 하는 행동. 첫 줄이 가장 중요한 행동이다 | 1. 로그인 / 그 밖에: 비밀번호 찾기, 회원가입으로 이동 |
| 출력 형태 | `output` | 무엇을 받을지. 묻지 않는다 | `prototype+figma` |

- 가장 중요한 행동(`actions` 첫 줄)은 1개만 둔다. 후보가 2개 이상이면 사람에게 하나를 고르게 한다 (`docs/UX.md` "행동의 위계")
- 화면 상태(빈 화면·로딩·오류·완료 등)는 사람이 말했으면 `scope`에 적는다. 말하지 않았으면 9장 기본값을 쓴다

## 3. 있으면 좋은 항목

없어도 화면을 만들 수 있다. 사람이 말했을 때만 적는다

| 항목 | 키 | 무엇을 적나 |
| --- | --- | --- |
| 참고 화면 | `reference` | 비슷하게 만들고 싶은 서비스나 화면 (링크·이미지·이름) |
| 메모 | `notes` | 그 밖에 꼭 지킬 것 |

- 참고 화면은 구성만 참고한다. 분위기·스타일은 따라 하지 않는다. 스타일은 테마로만 바꾼다 (`AGENTS.md` "프로젝트")
- 다른 서비스의 문구·이미지를 그대로 쓰지 않는다
- 테마는 적지 않는다. 화면은 기본 테마로 만들고, 테마는 `/theme`에서 고른다
- 사용자 상황(누가, 어떤 상황에서, 얼마나 익숙한지)은 따로 칸을 두지 않고 `goal`에 함께 적는다

## 4. 쉬운 화면과 어려운 화면

요청에 빠진 항목이 있을 때, Claude가 알아서 채울지 먼저 물을지를 정하는 기준이다

### 4-1. 질문 2개로 나눈다

**질문 1. 틀리면 위험한 화면인가?** 아래 중 하나라도 있으면 "예"

- 되돌릴 수 없는 행동이 있다. 무엇이 해당하는지는 `docs/UX.md` "위험한 행동"을 따른다 (예: 결제, 송금, 탈퇴)
- 약관 동의처럼 '~합니다' 말투를 쓰는 엄격한 화면이다 (`strict: true`)
- 민감한 개인정보를 다룬다: 건강, 신분증, 계좌, 위치. 로그인의 아이디·비밀번호는 넣지 않는다

**질문 2. 사람마다 다르게 만들 화면인가?** 아래 중 하나라도 있으면 "예"

- "홈", "대시보드", "내 맞춤"처럼 서비스마다 내용이 다른 화면이다
- 여러 단계 중 한 단계이거나, 조건에 따라 내용이 바뀐다 (예: 회원가입 2단계, 회원·비회원에 따라 다른 화면)
- 같은 강조로 나란히 놓일 버튼이 2개 이상이다 (예: 상품 상세의 "구매하기"와 "장바구니 담기")

### 4-2. 결과

| 질문 1 | 질문 2 | 결과 | Claude가 하는 일 |
| --- | --- | --- | --- |
| 아니요 | 아니요 | 쉬운 화면 | 빠진 항목을 추천 값으로 채운다. 만들기 전에 "이렇게 채웠어요"로 한 번 확인받는다 |
| 예 | 아무거나 | 어려운 화면 | 빠진 항목을 먼저 묻는다 |
| 아무거나 | 예 | 어려운 화면 | 빠진 항목을 먼저 묻는다 |

- 쉬운지 어려운지 헷갈리면 어려운 화면으로 본다
- 사람이 "알아서 해줘"라고 하면 쉬운 화면처럼, "하나씩 물어봐줘"라고 하면 어려운 화면처럼 한다
- 단, 질문 1이 "예"인 위험한 화면은 "알아서 해줘"라고 해도 묻는다

| 요청 | 질문 1 | 질문 2 | 결과 |
| --- | --- | --- | --- |
| 로그인 화면 | 아니요 | 아니요 | 쉬운 화면 |
| 알림 목록 | 아니요 | 아니요 (알림 누르기가 가장 중요하고, 모두 읽음은 보조) | 쉬운 화면 |
| 회원 탈퇴 | 예 (되돌릴 수 없음) | 아니요 | 어려운 화면 |
| 상품 상세 | 아니요 | 예 (같은 강조의 버튼이 2개) | 어려운 화면 |

## 5. 질문 규칙

- 목적·시나리오(`goal`)가 없으면 쉬운 화면이어도 가장 먼저 묻는다. 목적·시나리오는 추천 값으로 채우지 않는다 (`docs/UX.md` "AI 작업 규칙")
- 질문은 브리프 1개마다 최대 3개다 (`AGENTS.md` "스킬"). 이미 말한 것은 다시 묻지 않는다
- 확인 단계에서 "고칠게요"라고 한 뒤 다시 묻는 질문도 3개에 센다
- 3개를 다 물어도 빈 항목이 남으면 추천 값으로 채운다
- 어려운 화면은 목적·시나리오 → 가장 중요한 행동 → 범위 → 핵심 콘텐츠 순서로 묻는다
- 플랫폼·출력 형태는 묻지 않는다
- 묻지 않고 채운 항목은 브리프의 "Claude가 채운 항목"에 적고, 6장 확인 단계에서 알린다
- 기본으로 한 번에 하나씩 묻는다. 사람이 한꺼번에 물어 달라고 하면 그렇게 한다
- 질문마다 고를 수 있는 답 2~4개와 "직접 입력"을 준다. 추천하는 답에 표시한다
- 질문에 "모르겠어요"라고 하면 추천 답을 쓰고, 무엇을 골랐는지 알린다

질문 예시 (상품 상세):

```plain text
Claude: 이 화면에서 가장 중요한 버튼은 무엇인가요?
  ① 구매하기 (추천)
  ② 장바구니 담기
  ③ 직접 입력
```

### 5-1. 없는 UI가 필요할 때

- MVP 컴포넌트와 `DESIGN.md`에 없는 UI가 필요하면 브리프를 확정하지 않고 묻는다 (`AGENTS.md` "확정된 기준"의 "없는 UI는 만들지 않는다")
- 새로 만들어야 하면 "시스템 관리자에게 요청이 필요하다"고 알린다 (`AGENTS.md` "역할과 작업 범위")
- 이 질문은 3개 제한에 세지 않는다
- `/brief`는 요청에 이름이 나온 UI만 확인한다 (예: "지도 넣어줘"). 나머지는 `/generate-screen`이 구성 계획을 세울 때 확인한다
- 묻는 방법은 `docs/UX.md` "AI 작업 규칙"을 따른다

## 6. 확인·확정·수정

- 브리프를 다 채우면 사람에게 짧게 보여 주고 확인받는다. 확인받기 전에는 화면을 만들지 않는다
- `/generate-screen`이 `/brief`를 불렀으면, 브리프 확인을 구성 계획 확인과 한 번에 받는다. 같은 걸 두 번 묻지 않기 위해서다
- 확인할 때 6개 항목을 한 줄씩 보여 주고, Claude가 채운 항목에 표시한다
- 확정한 뒤 목적·범위·핵심 콘텐츠·주요 액션이 바뀌면 브리프를 먼저 고치고, 바뀐 부분만 다시 확인받는다
- 문구·위치·크기만 바뀌는 수정은 브리프를 고치지 않는다

## 7. 템플릿

`briefs/YYMMDD-topic.md`는 이 모양으로 만든다

- 맨 위 `---` 사이는 1장에서 Claude가 알아서 채우는 칸이다
- 제목 옆 괄호는 키다. `request`는 1장, 나머지는 2장·3장의 키다
- "Claude가 채운 항목"에는 묻지 않고 채운 것만 적는다. 늘 같은 값(`platform`·`output`)은 적지 않는다

```markdown
---
owner: <Git 사용자 이름>
platform: app
output: prototype+figma
strict: false
level: <easy 또는 hard>
---

# <화면 이름>

## 요청 원문 (request)
<사람이 처음 한 말 그대로>

## 목적·시나리오 (goal)
<누가, 어떤 상황에서, 무엇을 하려고>

## 범위 (scope)
- 만드는 것: <화면·상태>
- 만들지 않는 것: <제외>

## 핵심 콘텐츠 (content)
- <꼭 보여야 하는 정보>

## 주요 액션 (actions)
1. <가장 중요한 행동 1개>
- <그 밖의 행동>

## 참고 화면 (reference, 선택)
- <참고 화면>

## 메모 (notes, 선택)
- <그 밖에 지킬 것>

## Claude가 채운 항목
- <항목: 채운 값>
```

## 8. 예시

"알림 목록 화면 만들어줘"라는 요청으로 만든 브리프다. 알림 목록은 쉬운 화면이라 Claude가 목적만 묻고 나머지는 추천 값으로 채웠다. 파일 이름은 `briefs/261021-notification-list.md`다

```markdown
---
owner: example-user
platform: app
output: prototype+figma
strict: false
level: easy
---

# 알림 목록

## 요청 원문 (request)
알림 목록 화면 만들어줘

## 목적·시나리오 (goal)
앱을 쓰는 사용자가 푸시 알림을 놓친 뒤, 받은 알림을 모아 보고 필요한 것을 눌러 해당 화면으로 간다

## 범위 (scope)
- 만드는 것: 알림 목록 화면의 정상·빈·오류 상태
- 만들지 않는 것: 알림 설정 화면, 알림을 누른 뒤 열리는 화면

## 핵심 콘텐츠 (content)
- 알림 제목과 내용 한 줄
- 받은 시간
- 읽음·안 읽음 표시

## 주요 액션 (actions)
1. 알림을 눌러 해당 화면으로 이동
- 모두 읽음으로 표시

## Claude가 채운 항목
- 범위: 요청한 화면 1개, 만들지 않는 것은 Claude 추천
- 화면 상태: 정상·빈·오류
- 핵심 콘텐츠·주요 액션: Claude 추천 (쉬운 화면)
- 엄격한 화면: 아니요 (`strict: false`)
```

## 10. 출력 형태 값

지금은 값이 하나다. 프로토타입과 피그마 화면은 같은 이름의 한 쌍이고, 피그마는 코드에서 만든 사본이다 (`AGENTS.md` "프로젝트")

| 값 | 뜻 |
| --- | --- |
| `prototype+figma` | 프로토타입 링크 + 같은 이름의 피그마 Generated 화면 |

## 확정 전 점검표

`/brief`가 브리프를 확정하기 전에 스스로 점검한다

### 내용

- [ ] 요청 원문을 고치지 않고 그대로 적었다 (개인정보만 `[개인정보]`로)
- [ ] 꼭 채울 항목 6개가 다 있다
- [ ] 목적·시나리오에 누가, 어떤 상황에서, 무엇을 하려는지가 있다
- [ ] 가장 중요한 행동이 1개다
- [ ] 범위에 만들지 않는 것이 있다
- [ ] 화면이 1개다
- [ ] 묻지 않고 채운 항목을 "Claude가 채운 항목"에 적었다

### 질문·확인

- [ ] 쉬운 화면인지 어려운 화면인지 4장 기준으로 나누고 `level`에 적었다. 헷갈리면 `hard`로 봤다
- [ ] 목적·시나리오가 없으면 가장 먼저 물었다
- [ ] 질문이 브리프 1개마다 3개를 넘지 않았다 (없는 UI 질문은 빼고 센다)
- [ ] 없는 UI가 필요하면 확정하지 않고 물었다
- [ ] 사람에게 보여 주고 확인받았다 (`/generate-screen`이 불렀으면 구성 계획 확인 때)

### 하지 않는 것

- [ ] 디자인 값(색·간격·라운드)을 적지 않았다
- [ ] 테마를 적지 않았다
- [ ] 실제 사람의 개인정보를 넣지 않았다. `owner`에 성이 없다
- [ ] 다른 서비스의 문구·이미지를 그대로 옮기지 않았다
