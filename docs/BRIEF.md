# BRIEF.md

> 상태: 초안 v0.1 · 담당: 지수 · 태스크: 1-6
> 이 문서는 **화면 요청서(브리프)를 어떻게 쓰는지**에 대한 규칙입니다.
> 다루는 범위: 브리프 파일 · 필수/선택 항목 · 질문 · 확인 · 템플릿 · 기본값
> 사람이 "로그인 화면 만들어줘"처럼 말하면, Claude가 이 규칙대로 브리프 파일을 만들고 그 파일을 보고 화면을 만듭니다.
> 화면 모양·값은 `DESIGN.md`, 동작은 `docs/UX.md`, 문구는 `docs/WRITING.md`, 화면 유형별 구성은 `docs/PATTERNS.md`를 따릅니다.

---

## 0. 읽는 법

### 0-1. 규칙 강도

`docs/UX.md`와 같은 표시를 씁니다.

| 표시 | 뜻 | Claude의 행동 |
| --- | --- | --- |
| **[필수]** | 반드시 지킴 | 지킬 수 없으면 브리프를 확정하기 전에 사람에게 묻는다 |
| **[권장]** | 기본으로 따름 | 사람이 다르게 요청하면 그것을 따른다 |
| `[결정 필요]` | 팀 확정 전 | 함께 적힌 임시 기본값을 따른다 (10장) |

### 0-2. 브리프가 쓰이는 흐름

순서의 기준은 `AGENTS.md` "스킬"입니다. 아래는 이해를 돕는 그림입니다.

```plain text
사람: "○○ 화면 만들어줘"
  → /brief            자연어 요청을 브리프 파일로 정리 (빠진 것만 질문)
  → /generate-screen  브리프 → 구성 계획 → 사람 확인 → 프로토타입·피그마 생성
  → /theme (선택)      테마 프리셋 적용·비교
  → /ui-review        UX.md·WRITING.md 기준으로 점검
```

- 보통 사람은 `/brief`를 직접 부르지 않습니다. `/generate-screen`이 시작할 때 자동으로 거칩니다
- 사람은 명령어를 몰라도 됩니다. "화면 만들어줘"라고만 해도 이 흐름으로 시작합니다

## 1. 브리프 파일

| 항목 | 규칙 |
| --- | --- |
| 위치 | `briefs/` 폴더 |
| 파일 이름 | `YYMMDD-topic.md` (예: `261019-login.md`). 프로토타입 폴더·피그마 프레임과 같은 이름 (`docs/CONVENTIONS.md`) |
| 화면 주인 | 브리프의 `owner` 값이 화면 주인이다. 주인만 그 화면을 고친다 (`AGENTS.md` "역할과 작업 범위") |
| 화면 1개 | 브리프 1개 = 화면 1개 = 프로토타입 링크 1개 |

Claude가 자동으로 채우는 항목입니다. 사람에게 묻지 않습니다.

| 키 | 값 |
| --- | --- |
| `owner` | 지금 작업하는 사람의 GitHub 계정 이름 (`AGENTS.md` "역할과 작업 범위"의 화면 주인). 실명이 들어가면 성을 뺀다 |
| `date` | 브리프를 만든 날짜 (`YYYY-MM-DD`) |

- **[필수]** 다른 사람이 `owner`인 브리프는 읽기만 한다
- **[필수]** 브리프에는 색·간격·라운드 같은 디자인 값을 적지 않는다. 값은 `DESIGN.md`가 정한다
- **[필수]** 저장소가 공개라서 브리프와 예시 데이터에 실제 사람의 이름·이메일·전화번호 같은 개인정보를 넣지 않는다. 예시 데이터는 지어낸 값만 쓴다 (`AGENTS.md` "확정된 기준")
- **[필수]** 한 브리프에 화면이 여러 개 섞이면 화면별로 나눈다 (`docs/UX.md` 2장 "한 화면은 하나의 목적")

---

## 2. 필수 항목 6개

`AGENTS.md` "스킬"에서 정한 필수 항목입니다. 6개가 모두 채워져야 화면을 만들기 시작합니다. 키는 영어, 설명은 한글로 씁니다 (`docs/CONVENTIONS.md` "MD 작성").

| 항목 | 키 | 무엇을 적나 | 예시 (로그인 화면) |
| --- | --- | --- | --- |
| 목적·시나리오 | `goal` | 누가, 어떤 상황에서, 무엇을 하려고 이 화면에 오는지 | 처음 앱을 연 사용자가 기존 계정으로 들어간다 |
| 플랫폼 | `platform` | 앱(모바일)으로 고정. 묻지 않고 자동으로 채운다 | `app` |
| 범위 | `scope` | 이번에 만들 화면과 상태. 만들지 않는 것도 적는다 | 로그인 화면의 정상·오류 상태. 회원가입은 제외 |
| 핵심 콘텐츠 | `content` | 화면에 꼭 보여야 하는 정보 | 이메일 입력, 비밀번호 입력, 비밀번호 찾기 링크 |
| 주요 액션 | `actions` | 사용자가 할 수 있는 행동. 가장 중요한 1개를 먼저 | 로그인(주요), 비밀번호 찾기, 회원가입으로 이동 |
| 출력 형태 | `output` | 무엇을 받을지. 묻지 않고 기본값으로 채운다 | `prototype+figma` |

- **[필수]** 주요 액션은 1개만 적는다 (`docs/UX.md` 4-1). 2개 이상이면 사람에게 하나를 고르게 한다
- **[권장]** `scope`에 화면 상태(빈 화면·로딩·오류·완료 등)를 함께 적는다. 적지 않으면 9장의 기본값을 따른다

## 3. 선택 항목

없어도 화면을 만들 수 있습니다. 사람이 말했을 때만 적습니다.

| 항목 | 키 | 무엇을 적나 |
| --- | --- | --- |
| 참고 화면 | `reference` | 비슷하게 만들고 싶은 서비스나 화면 (링크·이미지·이름) |
| 엄격한 화면 여부 | `strict` | 결제·약관처럼 '~합니다' 말투가 필요한 화면인지 (`AGENTS.md` "확정된 기준"의 문구 말투) |
| 메모 | `notes` | 그 밖에 꼭 지켜야 할 것 |

- **[필수]** 참고 화면은 구성만 참고한다. 다른 서비스의 문구·이미지를 그대로 쓰지 않는다
- `[결정 필요]` 참고 화면을 어디까지 따를지(구성만 / 분위기까지)를 브리프에 적게 할지. 임시 기본값: 적지 않고 구성만 참고한다
- `[결정 필요]` 사용자 환경(누가, 어떤 상황에서, 얼마나 익숙한지)을 따로 적을지. 임시 기본값: 따로 두지 않고 `goal`에 함께 적는다
- **[필수]** 테마는 브리프에 적지 않는다. 화면은 기본 테마로 만들고, 테마는 `/theme` 단계에서 고른다 (`AGENTS.md` "스킬")

## 4. 질문 규칙

사람 말에 빠진 필수 항목이 있을 때 Claude가 묻는 방법입니다.

- **[필수]** 질문은 **최대 3개**다 (`AGENTS.md` "스킬"). 이미 말한 것은 다시 묻지 않는다
- **[필수]** 목적·시나리오가 없으면 반드시 묻는다 (`docs/UX.md` 13장 "사용자의 상황이 없으면 묻는다")
- **[권장]** 나머지 항목은 목적에서 추론할 수 없을 때만 묻는다. 묻는 순서는 주요 액션 → 범위 → 핵심 콘텐츠다. 플랫폼·출력 형태는 기본값이라 묻지 않는다
- **[필수]** 묻지 않은 빈 항목은 9장의 기본값으로 채우고, 5장 확인 단계에서 그 사실을 알린다
- **[권장]** 한 번에 하나씩 묻는다
- **[권장]** 질문마다 고를 수 있는 선택지 2~4개 + 직접 입력을 준다. 추천하는 것을 표시한다
- **[권장]** "모르겠어요", "알아서 해줘"라고 하면 9장의 기본값을 쓰고 무엇을 골랐는지 알린다
- **[필수]** 요청 단계에서 이미 MVP 컴포넌트(`AGENTS.md` "확정된 기준")에 없는 UI가 필요하다고 드러나면 브리프를 확정하지 않고 묻는다 (`AGENTS.md` "없는 UI는 만들지 않는다"). 이 질문은 3개 제한에 넣지 않는다. 화면 구성에 쓸 컴포넌트는 `/generate-screen`이 정한다

질문 예시:

```plain text
Claude: 이 화면은 누가, 어떤 상황에서 보나요?
  ① 새 소식을 확인하려는 기존 사용자 (추천)
  ② 처음 앱을 연 사용자
  ③ 직접 입력
```

## 5. 확인·확정·수정

- **[필수]** 브리프를 다 채우면 사람에게 요약해서 보여 주고 확인받는다. 확인받기 전에는 화면을 만들지 않는다
- **[권장]** `/generate-screen`이 `/brief`를 부른 경우, 브리프 요약은 구성 계획과 함께 한 번에 확인받아 같은 내용을 두 번 묻지 않는다. 구성 계획 확인 방식은 `/generate-screen`이 정한다
- **[권장]** 요약은 6개 항목을 한 줄씩 보여 준다. 기본값으로 채운 항목은 표시한다
- **[권장]** 확정한 뒤 목적·범위·핵심 콘텐츠·주요 액션이 바뀌는 요청이 오면, 브리프를 먼저 고치고 바뀐 부분만 다시 확인받는다
- **[권장]** 문구·위치·크기처럼 위 4개 항목이 바뀌지 않는 수정은 브리프를 고치지 않는다

## 6. 템플릿

`briefs/YYMMDD-topic.md`는 이 모양으로 만듭니다. 제목 옆 괄호는 2·3장의 키입니다.

```markdown
---
owner: <GitHub 계정 이름>
date: YYYY-MM-DD
platform: app
output: prototype+figma
strict: false
---

# <화면 이름>

## 목적·시나리오 (goal)
<누가, 어떤 상황에서, 무엇을 하려고>

## 범위 (scope)
- 만드는 것: <화면·상태>
- 만들지 않는 것: <제외>

## 핵심 콘텐츠 (content)
- <꼭 보여야 하는 정보>

## 주요 액션 (actions)
1. <주요 액션 1개>
- <그 밖의 행동>

## 참고 화면 (reference, 선택)
- <참고 화면>

## 메모 (notes, 선택)
- <그 밖에 지킬 것>

## 기본값으로 채운 항목
- <항목: 고른 값>
```

## 7. 예시

"알림 목록 화면 만들어줘"라는 요청에 Claude가 목적만 물어보고 만든 브리프입니다. 나머지는 목적에서 추론하거나 기본값으로 채웠습니다.

```markdown
---
owner: example-user
date: 2026-10-19
platform: app
output: prototype+figma
strict: false
---

# 알림 목록

## 목적·시나리오 (goal)
앱을 쓰는 사용자가 푸시 알림을 놓친 뒤, 받은 알림을 모아 보고 필요한 것을 눌러 해당 화면으로 간다.

## 범위 (scope)
- 만드는 것: 알림 목록 화면의 정상·빈·오류 상태
- 만들지 않는 것: 알림 설정 화면, 알림을 누른 뒤 열리는 화면

## 핵심 콘텐츠 (content)
- 알림 제목과 내용 한 줄
- 받은 시간
- 읽음·안 읽음 표시

## 주요 액션 (actions)
1. 알림을 눌러 해당 화면으로 이동
- 모두 읽음으로 표시

## 기본값으로 채운 항목
- 범위: 요청한 화면 1개. 만들지 않는 것은 목적에서 추론
- 화면 상태: 정상·빈·오류
- 핵심 콘텐츠·주요 액션: 목적에서 추론
```

---

## 8. 출력 형태 값

지금은 값이 하나입니다. 프로토타입과 피그마 Generated 화면은 같은 이름의 한 쌍이고, 피그마는 코드에서 만든 사본이기 때문입니다 (`AGENTS.md` "프로젝트").

| 값 | 뜻 |
| --- | --- |
| `prototype+figma` | 프로토타입 링크 + 같은 이름의 피그마 Generated 프레임 |

---

## 9. 기본값

사람이 말하지 않았을 때 채우는 값입니다. 모두 이미 정해진 규칙에서 가져왔습니다.

| 항목 | 기본값 | 근거 |
| --- | --- | --- |
| 플랫폼 | `app` | `AGENTS.md` "확정된 기준": 만드는 화면은 앱 화면(모바일) |
| 출력 형태 | `prototype+figma` | `AGENTS.md` "스킬": `/generate-screen`이 프로토타입·피그마를 만든다 |
| 화면 상태 | 정상·빈·오류 | `docs/UX.md` 13장 "상태 범위가 없으면 정상·빈·오류" |
| 범위 | 요청한 화면 1개 | 1장 "브리프 1개 = 화면 1개" |
| 핵심 콘텐츠 · 주요 액션 | 목적·시나리오에서 추론한다 | 5장 확인 단계에서 사람이 보고 고친다. `[결정 필요]` (10장 3번) |

---

## 10. 결정 기록

본문의 `[결정 필요]`는 팀이 확정하면 확정 문장으로 바꾸고 여기에 남깁니다. 새로 결정이 필요한 항목이 생기면 본문에 `[결정 필요]`와 임시 기본값을 적고 이 표에 추가합니다.

| 번호 | 항목 | 위치 | 결정 |
| --- | --- | --- | --- |
| 1 | 참고 화면을 따르는 정도를 적게 할지 | 3장 | 미정 |
| 2 | 사용자 환경을 따로 적을지 | 3장 | 미정 |
| 3 | 핵심 콘텐츠·주요 액션을 묻지 않고 추론으로 채워도 되는지 | 4장 · 9장 | 미정 |

## 참고 자료

다른 AI 화면 생성 도구가 요청을 받는 방식을 비교했습니다. 방식만 참고하고 문장은 새로 씁니다.

| 비교 | v0 (Vercel) | Stitch (Google) | Figma Make | 이 문서 |
| --- | --- | --- | --- | --- |
| 요청에 넣으라고 권하는 것 | 계획 먼저, 맥락, 구체적으로, 되묻게 하기 | 구조 · 분위기 · 콘텐츠 3층 | 확인 못 함 | 2장 필수 항목 6개 |
| 만들기 전 정리 단계 | 복잡하면 계획부터 | 확인 못 함 | Plan mode: 계획을 검토·수정한 뒤 생성 | 5장 확인, `/generate-screen` 구성 계획 |
| 상태 | 오류·빈 화면·로딩을 적으라고 권함 | 확인 못 함 | 확인 못 함 | 9장 기본값 (`docs/UX.md` 13장) |
| 분위기·스타일 | 확인 못 함 | 형용사로 분위기를 정함 | 확인 못 함 | 브리프에 적지 않음. `/theme`에서 고름 |

- v0: [Text Prompting](https://v0.app/docs/text-prompting) · [How to prompt v0](https://vercel.com/blog/how-to-prompt-v0)
- Stitch: [Prompt Framework (llms.txt)](https://stitch.withgoogle.com/llms.txt)
- Figma Make: [Use plan mode in Figma Make](https://help.figma.com/hc/en-us/articles/40830441709719-Use-plan-mode-in-Figma-Make)

## 확정 전 점검표

`/brief`가 브리프를 확정하기 전에 스스로 점검합니다. 화면을 점검하는 `/ui-review`의 점검 대상은 아닙니다.

### 항목

- [ ] 필수 항목 6개가 모두 채워져 있다
- [ ] 목적·시나리오에 누가, 어떤 상황에서, 무엇을 하려는지가 있다
- [ ] 주요 액션이 1개다
- [ ] 범위에 만들지 않는 것이 적혀 있다
