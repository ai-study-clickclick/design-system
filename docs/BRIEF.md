# BRIEF.md

> 상태: 초안 v0.4 · 태스크: 1-6

화면 요청서(브리프)를 만드는 규칙이다

사람이 "로그인 화면 만들어줘"라고 말하면 Claude는 이 규칙대로 브리프 파일을 만든다. 화면은 그 브리프를 보고 만든다

이 문서는 "무엇을 만들지"만 정한다. 나머지는 아래 문서를 따른다

| 무엇 | 따르는 문서 |
| --- | --- |
| 색·크기·라운드 같은 디자인 값 | `DESIGN.md` |
| 화면 동작 · 화면 상태 | `docs/UX.md` |
| 문구 · 엄격한 화면 기준 | `docs/WRITING.md` |
| 화면 유형별 구성 | `docs/PATTERNS.md` |
| 규칙 표시·문서 형식 | `docs/CONVENTIONS.md` "MD 작성" |

---

## 0. 브리프가 쓰이는 순서

```plain text
사람: "○○ 화면 만들어줘"
  → /brief            요청을 브리프 파일로 정리한다
  → /generate-screen  브리프를 보고 구성 계획을 세우고, 사람이 확인하면 화면을 만든다
  → /theme (선택)      테마를 바꿔 본다
  → /ui-review        만든 화면을 점검한다
```

- 순서의 기준은 `AGENTS.md` "스킬"이다
- 사람은 명령어를 몰라도 된다. "화면 만들어줘"라고만 해도 이 순서로 시작한다
- `/brief`는 보통 `/generate-screen`이 시작할 때 자동으로 부른다

## 1. 브리프 파일

| 항목 | 규칙 |
| --- | --- |
| 위치 | `briefs/` 폴더 |
| 파일 이름 | `YYMMDD-topic.md` (예: `261021-login.md`). 이름 규칙은 `docs/CONVENTIONS.md` "공통 이름 규칙"·"코드·피그마"를 따른다. 여러 단계 흐름은 1-1을 따른다 |
| 화면 1개 | 브리프 1개 = 화면 1개 = 프로토타입 링크 1개 |
| 화면 주인 | `owner`에 적힌 사람이다 (`AGENTS.md` "역할과 작업 범위") |

Claude가 묻지 않고 알아서 채우는 칸이다

| 키 | 값 |
| --- | --- |
| `owner` | 지금 작업하는 사람의 GitHub 아이디 (`gh api user --jq .login`) |
| `platform` | 늘 `app` |
| `output` | 늘 `prototype` (10장) |
| `strict` | 보통 `false`. `docs/WRITING.md`의 엄격한 화면에 해당하면 `true` |
| `level` | 4장 기준으로 나눈 결과. 쉬운 화면이면 `easy`, 어려운 화면이면 `hard`. "알아서 해줘"처럼 묻는 방식이 바뀌어도 그대로 둔다 |

- `[결정 필요]` 엄격한 화면 기준은 `docs/WRITING.md`가 정한다. 그 문서에 기준이 생기기 전까지는 결제·약관처럼 '~합니다' 말투가 필요한 화면을 `true`로 한다 (`AGENTS.md` "확정된 기준"의 화면 문구 말투)
- `owner`에는 GitHub 아이디를 그대로 쓴다 (`AGENTS.md` "역할과 작업 범위"). 이미 공개된 값이고 사람마다 하나라서, PC가 달라도 같은 값이 된다
- GitHub 아이디를 읽지 못하면(로그인 안 됨 등) 사람에게 묻는다
- 색·간격·라운드 같은 디자인 값은 적지 않는다. 값은 `DESIGN.md`가 정한다

### 1-1. 여러 화면 요청

- 화면이 여러 개 섞인 요청이나 여러 단계로 된 흐름은 화면마다 브리프를 나눈다 (`docs/UX.md` "정보 구조")
- 나누기 전에 화면 목록을 보여 주고 "어디부터 만들까요?"를 한 번 묻는다. Claude가 혼자 나누지 않는다
- 목적·시나리오처럼 모든 화면에 같은 질문은 처음에 한 번만 묻고, 나머지 브리프에 그대로 쓴다
- 질문 3개와 `level`은 화면마다 따로 센다 (4장 · 5장)
- 한 화면 안에서 넘겨 보는 슬라이드는 화면 1개로 본다
- 같은 흐름의 브리프는 "연관 화면"에 흐름 전체를 순서대로 적고 지금 화면을 표시한다 (7장)
- `[결정 필요]` 여러 단계 흐름의 파일 이름. 임시로 같은 날짜·주제 뒤에 단계 번호와 단계 이름을 붙인다 (예: `261112-return-1-select.md`, `261112-return-2-reason.md`, `261112-return-3-done.md`)

### 1-2. 요청 원문과 개인정보

- 사람이 처음 한 말은 "요청 원문"(`request`)에 고치거나 줄이지 않고 그대로 적는다. 브리프가 무엇에서 시작했는지 나중에 확인하기 위해서다 (`docs/CONVENTIONS.md` "MD 작성")
- 확정 전에 더 말한 요청은 `request`에 붙이지 않고 "추가 요청"에 한 줄씩 적는다
- 요청 원문에 사람을 알아볼 수 있는 정보(이름·이메일·전화번호·주민등록번호·주소 등)가 있으면 그 부분만 `[개인정보]`로 바꾼다. 진짜인지 지어낸 값인지 상관없이 바꾼다. 저장소가 공개라서다
- `[개인정보]`로 바꿨으면 확인 단계에서 알린다
- 브리프에 쓰는 예시 데이터는 지어낸 값만 쓴다

## 2. 꼭 채울 항목 6개

6개가 다 채워져야 화면을 만들기 시작한다. 항목은 `AGENTS.md` "스킬"을 따른다

| 항목 | 키 | 무엇을 적나 | 예시 (로그인 화면) |
| --- | --- | --- | --- |
| 목적·시나리오 | `goal` | 누가, 어떤 상황에서, 무엇을 하려고 이 화면에 오나 | 처음 앱을 연 사용자가 기존 계정으로 들어간다 |
| 플랫폼 | `platform` | 늘 앱(모바일). 묻지 않는다 | `app` |
| 범위 | `scope` | 이번에 만들 화면과 상태. 만들지 않는 것도 적는다 | 로그인 화면의 정상·기다림·실패 상태. 회원가입은 만들지 않는다 |
| 핵심 콘텐츠 | `content` | 화면에 꼭 보여야 하는 정보 | 이메일 입력, 비밀번호 입력, 비밀번호 찾기 링크 |
| 주요 액션 | `actions` | 사용자가 누르는 행동. 첫 줄이 가장 중요한 행동이다 | 1. 로그인 / 그 밖에: 비밀번호 찾기, 회원가입으로 이동 |
| 출력 형태 | `output` | 무엇을 받을지. 묻지 않는다 | `prototype` |

- 가장 중요한 행동(`actions` 첫 줄)은 1개만 둔다. 후보가 2개 이상이면 사람에게 하나를 고르게 한다 (`docs/UX.md` "행동의 위계")
- `actions`에는 누르는 행동만 적는다. "한눈에 보기"처럼 보는 것은 목적·시나리오에 적는다
- 보기만 하는 화면(예: 대시보드)은 가장 자주 누를 행동을 첫 줄에 적는다. 누를 행동이 없으면 첫 줄에 "없음 (보기만 하는 화면)"이라 적고 주된 버튼을 만들지 않는다
- 화면 상태는 사람이 말했으면 `scope`에 적는다. 말하지 않았으면 `docs/UX.md` "화면 성격별 묶음"을 따른다

## 3. 있으면 좋은 항목

없어도 화면을 만들 수 있다. 사람이 말했을 때만 적는다

| 항목 | 키 | 무엇을 적나 |
| --- | --- | --- |
| 참고 화면 | `reference` | 비슷하게 만들고 싶은 서비스나 화면 (링크·이미지·이름) |
| 메모 | `notes` | 그 밖에 꼭 지킬 것 |

- Claude가 적고 싶은 메모는 `notes`가 아니라 "Claude가 채운 항목"에 적는다
- 참고 화면은 구성만 참고한다. 분위기·스타일은 따라 하지 않는다. 스타일은 테마로만 바꾼다 (`AGENTS.md` "프로젝트")
- 다른 서비스의 문구·이미지를 그대로 쓰지 않는다
- 테마는 적지 않는다. 화면은 기본 테마로 만들고, 테마는 `/theme`에서 고른다
- 사용자 상황(누가, 어떤 상황에서, 얼마나 익숙한지)은 따로 칸을 두지 않고 `goal`에 함께 적는다

## 4. 쉬운 화면과 어려운 화면

요청에 빠진 항목이 있을 때, Claude가 알아서 채울지 먼저 물을지를 정하는 기준이다

### 4-1. 질문 2개로 나눈다

**질문 1. 틀리면 위험한 화면인가?** 아래에 해당하면 "예"

- 되돌릴 수 없는 행동이 있다. 무엇이 해당하는지는 `docs/UX.md` "위험한 행동"을 따른다 (예: 결제, 송금, 탈퇴)
- 위험한지 여부가 서비스 정책에 달렸으면 짐작으로 "아니요"로 정하지 않는다. 짐작한 값은 ⚠️로 확인받는다 (5-3)
- 엄격한 화면(`strict: true`)인지는 이 질문에 쓰지 않는다. `strict`는 말투를 정할 때만 쓴다

**질문 2. 사람마다 다르게 만들 화면인가?** 아래 중 하나라도 있으면 "예"

- "홈", "대시보드", "내 맞춤"처럼 서비스마다 내용이 다른 화면이다
- 여러 단계 중 한 단계이거나, 보는 사람의 조건에 따라 내용이 바뀐다 (예: 회원가입 2단계, 회원·비회원에 따라 다른 화면)
- 가장 중요한 행동 후보가 2개 이상이다 (예: 상품 상세의 "구매하기"와 "장바구니 담기")
- 보는 사람과 상관없이 데이터만 바뀌는 것은 해당하지 않는다

### 4-2. 결과

| 질문 1 | 질문 2 | 결과 | Claude가 하는 일 |
| --- | --- | --- | --- |
| 아니요 | 아니요 | 쉬운 화면 | 빠진 항목을 추천 값으로 채운다. 만들기 전에 한 번 확인받는다 |
| 예 | 아무거나 | 어려운 화면 | 빠진 항목을 먼저 묻는다 |
| 아무거나 | 예 | 어려운 화면 | 빠진 항목을 먼저 묻는다 |

- 쉬운지 어려운지 헷갈리면 어려운 화면으로 본다
- 사람이 "알아서 해줘"라고 하면 쉬운 화면처럼, "하나씩 물어봐줘"라고 하면 어려운 화면처럼 한다
- 단, 질문 1이 "예"인 위험한 화면은 "알아서 해줘"라고 해도 묻는다
- 범위가 커지거나 가장 중요한 행동이 바뀌면 `level`을 다시 본다

| 요청 | 질문 1 | 질문 2 | 결과 |
| --- | --- | --- | --- |
| 로그인 화면 | 아니요 | 아니요 | 쉬운 화면 |
| 알림 목록 | 아니요 | 아니요 (알림 누르기가 가장 중요하고, 모두 읽음은 보조) | 쉬운 화면 |
| 회원 탈퇴 | 예 (되돌릴 수 없음) | 아니요 | 어려운 화면 |
| 상품 상세 | 아니요 | 예 (가장 중요한 행동 후보가 2개) | 어려운 화면 |

## 5. 질문 규칙

### 5-1. 무엇을 묻나

- 목적·시나리오(`goal`)가 없으면 쉬운 화면이어도 가장 먼저 묻는다. 목적·시나리오는 Claude가 혼자 정하지 않는다 (`docs/UX.md` "AI 작업 규칙")
- 무엇을 다루는 서비스인지 없는 요청은 목적 질문의 선택지에 대상을 함께 넣는다
- 어려운 화면은 목적·시나리오 → 가장 중요한 행동 → 핵심 콘텐츠 → 범위 순서로 묻는다
- 플랫폼·출력 형태는 묻지 않는다
- 이미 말한 것은 다시 묻지 않는다

### 5-2. 몇 개 묻나

- 질문은 화면마다 최대 3개다 (`AGENTS.md` "스킬")
- 아래는 3개에 세지 않는다. 이런 질문도 하나씩 묻는다
  - 목적·시나리오 질문
  - 화면 목록에서 어디부터 만들지 고르는 질문 (1-1)
  - 사람이 되묻거나 용어를 물을 때의 답
  - 고칠 말이나 모호한 말을 되묻는 질문. 무엇을 고칠지·취소할지 모르면 짐작하지 않고 되묻는다
  - 없는 컴포넌트 질문 (5-4)
  - ⚠️ 확인 (5-3)
- 3개를 다 물어도 빈 항목이 남으면 추천 값으로 채운다. 단, 5-3의 항목은 ⚠️로 확인받는다

### 5-3. 어떻게 묻나

- 한 번에 하나씩 묻는다. 사람이 한꺼번에 물어 달라고 하면 그렇게 한다
- 질문은 한 문장으로 쓴다. 쉬운·어려운 화면, 위험한 화면, 엄격한 화면 같은 판단과 이유는 말하지 않는다. 판단은 브리프 파일에만 적는다
- 질문은 선택 창(Claude Code의 질문 창)으로 띄워 사람이 눌러서 고르게 한다. 번호나 답을 글로 치게 하지 않는다. 선택 창을 쓸 수 없는 곳에서만 글로 묻는다
- 질문마다 고를 수 있는 답 2~4개와 "직접 입력"을 준다. 추천하는 답에 표시한다
- 답은 짧은 말로 쓴다. 설명이 필요하면 한 줄만 붙인다
- 사람이 고른 답은 바꾸지 않고 그대로 적는다
- 질문에 "모르겠어요"라고 하면 추천 답을 쓰고, 그 자리에서 무엇을 골랐는지 알린다
- 아래 항목은 추천 값만으로 확정하지 않는다. 추천 값을 넣고 ⚠️를 붙여 확인받는다
  - 목적·시나리오
  - 위험한 화면(4장 질문 1이 "예")에서 Claude가 채운 항목. 질문 3개를 다 써서 못 물은 핵심 콘텐츠도 포함한다
  - Claude가 짐작으로 정한 값 (4장 질문 1)
- ⚠️ 확인도 하나씩 선택 창으로 묻는다. 사람이 답해야 확정한다

질문 예시 (상품 상세, 선택 창에 보이는 내용):

```plain text
Claude: 이 화면에서 가장 중요한 버튼은 무엇인가요?
  ① 구매하기 (추천)
  ② 장바구니 담기
  ③ 직접 입력
```

### 5-4. 없는 컴포넌트가 필요할 때

- 브리프에 넣으려는 컴포넌트가 MVP 컴포넌트와 `DESIGN.md`에 없으면 브리프를 확정하기 전에 묻는다. 요청에 이름이 나오지 않아도 같다
- "있는 컴포넌트로 만들까요, 새로 만들까요?"를 묻는다
- 있는 컴포넌트로 만들 때 요청의 핵심이 바뀌면 바뀐다고 알리고 목적·시나리오를 다시 확인한다
- 새로 만들 때는 화면을 만들면서 `DESIGN.md`를 참고해 만들고, 브리프 "새로 만든 컴포넌트"에 적는다. 그 화면의 프로토타입 폴더 안에만 만들고 `src/components/`에는 넣지 않는다 (`AGENTS.md` "역할과 작업 범위"). 디자인이 확정되고 필요하면 시스템 관리자에게 추가를 요청하고, 추가되면 그 컴포넌트로 바꾼다
- 고른 답은 브리프에 적고, 화면은 그대로 따른다

### 5-5. 목적이나 주제가 바뀔 때

- 뒤의 답이 앞에서 정한 목적을 바꾸면 바뀐 목적을 다시 확인한다
- 주제가 바뀌면 같은 대화에서 처음부터 다시 채운다. 이전 답은 쓰지 않는다

---

## 6. 확인·확정·수정

- 브리프를 다 채우면 저장하기 전에 브리프 전체를 보여 주고 확인받는다. 확인받기 전에는 파일을 저장·커밋하지 않고 화면도 만들지 않는다
- `/generate-screen`이 `/brief`를 불렀으면, 브리프 확인을 구성 계획 확인과 한 번에 받는다. 같은 걸 두 번 묻지 않기 위해서다
- 항목마다 한 줄로 보여 준다. Claude가 채운 항목에는 🤖를 붙인다
- ⚠️가 붙은 항목은 하나씩 답을 받는다 (5-3)
- 확인 중이나 확정한 뒤에 목적·범위·핵심 콘텐츠·주요 액션이 바뀌면 브리프를 먼저 고치고, 바뀐 부분만 다시 확인받는다
- 문구·위치·크기만 바뀌는 수정은 브리프를 고치지 않는다

---

## 7. 템플릿

`briefs/YYMMDD-topic.md`는 이 모양으로 만든다

- 맨 위 `---` 사이는 1장에서 Claude가 알아서 채우는 칸이다
- 제목 옆 괄호는 키다. `request`는 1장, 나머지는 2장·3장의 키다
- "(있을 때)"인 칸은 해당할 때만 둔다
- "Claude가 채운 항목"에는 묻지 않고 채운 것만 🤖를 붙여 적는다. 늘 같은 값(`platform`·`output`)은 적지 않는다

```markdown
---
owner: <GitHub 아이디>
platform: app
output: prototype
strict: false
level: <easy 또는 hard>
---

# <화면 이름>

## 요청 원문 (request)
<사람이 처음 한 말 그대로>

## 추가 요청 (있을 때)
- <확정 전에 더 말한 요청>

## 목적·시나리오 (goal)
<누가, 어떤 상황에서, 무엇을 하려고>

## 범위 (scope)
- 만드는 것: <화면·상태>
- 만들지 않는 것: <제외>

## 핵심 콘텐츠 (content)
- <꼭 보여야 하는 정보>

## 주요 액션 (actions)
1. <가장 중요한 행동 1개>
- <그 밖의 행동>

## 참고 화면 (reference, 선택)
- <참고 화면>

## 메모 (notes, 선택)
- <사람이 말한 그 밖에 지킬 것>

## 연관 화면 (있을 때)
1. briefs/<YYMMDD-topic-1-step>.md
2. briefs/<YYMMDD-topic-2-step>.md ← 지금 화면

## 새로 만든 컴포넌트 (있을 때)
- <컴포넌트: 왜 필요했는지>

## Claude가 채운 항목
- 🤖 <항목: 채운 값>
```

## 8. 예시

"알림 목록 화면 만들어줘"라는 요청으로 만든 브리프다. 알림 목록은 쉬운 화면이라 Claude가 목적만 묻고 나머지는 추천 값으로 채웠다. 파일 이름은 `briefs/261021-notification-list.md`다

```markdown
---
owner: example-user
platform: app
output: prototype
strict: false
level: easy
---

# 알림 목록

## 요청 원문 (request)
알림 목록 화면 만들어줘

## 목적·시나리오 (goal)
앱을 쓰는 사용자가 푸시 알림을 놓친 뒤, 받은 알림을 모아 보고 필요한 것을 눌러 해당 화면으로 간다

## 범위 (scope)
- 만드는 것: 알림 목록 화면의 정상·기다림·비어 있음·실패 상태
- 만들지 않는 것: 알림 설정 화면, 알림을 누른 뒤 열리는 화면

## 핵심 콘텐츠 (content)
- 알림 제목과 내용 한 줄
- 받은 시간
- 읽음·안 읽음 표시

## 주요 액션 (actions)
1. 알림을 눌러 해당 화면으로 이동
- 모두 읽음으로 표시

## Claude가 채운 항목
- 🤖 범위: 요청한 화면 1개, 만들지 않는 것은 Claude 추천
- 🤖 화면 상태: 정상·기다림·비어 있음·실패 (목록 화면)
- 🤖 핵심 콘텐츠·주요 액션: Claude 추천 (쉬운 화면)
- 🤖 엄격한 화면: 아니요 (`strict: false`)
```

## 9. 기본값

사람이 말하지 않았을 때 쓰는 값이다

| 항목 | 기본값 | 따르는 규칙 |
| --- | --- | --- |
| 플랫폼 | `app` | `AGENTS.md` "확정된 기준": 앱 화면(모바일)을 만든다 |
| 출력 형태 | `prototype` | 10장 |
| 엄격한 화면 | `false` | 1장 |
| 화면 상태 | 화면 성격에 맞는 상태 | `docs/UX.md` "화면 성격별 묶음"·"AI 작업 규칙" |
| 범위 | 요청한 화면 1개 | 1장 |
| 핵심 콘텐츠·주요 액션 | 쉬운 화면은 Claude가 추천 값으로 채운다. 어려운 화면은 묻는다 | 4장 |

## 10. 출력 형태 값

| 값 | 뜻 |
| --- | --- |
| `prototype` | 프로토타입 링크 |

- 화면은 프로토타입으로 먼저 만든다. 피그마 Generated 화면은 화면이 확정된 뒤 필요하면 `/sync`로 만든다 (`AGENTS.md` "프로젝트")

## 확정 전 점검표

`/brief`가 브리프를 확정하기 전에 스스로 점검한다

### 내용

- [ ] 요청 원문을 고치지 않고 그대로 적었다 (사람을 알아볼 수 있는 정보만 `[개인정보]`로)
- [ ] 확정 전에 더 말한 요청은 "추가 요청"에 따로 적었다
- [ ] 꼭 채울 항목 6개가 다 있다
- [ ] 목적·시나리오에 누가, 어떤 상황에서, 무엇을 하려는지가 있다
- [ ] 가장 중요한 행동이 1개이고, 누르는 행동이다 (보기만 하는 화면은 "없음")
- [ ] 범위에 만들지 않는 것이 있다
- [ ] 화면 상태 이름이 `docs/UX.md`의 이름이다
- [ ] 화면이 1개다. 여러 화면이면 목록을 보여 주고 확인받은 뒤 나눴다
- [ ] 같은 흐름이면 "연관 화면"을 적었다
- [ ] 묻지 않고 채운 항목을 🤖를 붙여 "Claude가 채운 항목"에 적었다
- [ ] `notes`에는 사람이 말한 것만 적었다
- [ ] 사람이 고른 답을 바꾸지 않고 적었다
- [ ] `owner`에 GitHub 아이디를 적었다

### 질문·확인

- [ ] 쉬운 화면인지 어려운 화면인지 4장 기준으로 나누고 `level`에 적었다. 헷갈리면 `hard`로 봤다
- [ ] 목적·시나리오가 없으면 가장 먼저 물었다
- [ ] 목적·시나리오 → 가장 중요한 행동 → 핵심 콘텐츠 → 범위 순서로 물었다
- [ ] 질문이 화면마다 3개를 넘지 않았다 (5-2에서 세지 않는 질문은 빼고 센다)
- [ ] 질문에 판단과 이유를 붙이지 않았다
- [ ] 질문과 ⚠️ 확인을 선택 창으로 하나씩 물었다
- [ ] 없는 컴포넌트가 필요하면 확정하지 않고 물었고, 고른 답을 적었다
- [ ] 목적이 바뀌었으면 다시 확인했다
- [ ] 저장하기 전에 브리프 전체를 보여 주고 확인받았다 (`/generate-screen`이 불렀으면 구성 계획 확인 때)

### 하지 않는 것

- [ ] 디자인 값(색·간격·라운드)을 적지 않았다
- [ ] 테마를 적지 않았다
- [ ] 사람을 알아볼 수 있는 정보를 넣지 않았다
- [ ] 다른 서비스의 문구·이미지를 그대로 옮기지 않았다
