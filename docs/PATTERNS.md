- 장면에 들어가는 문구는 `docs/WRITING.md` "상태별 문구" · "오류 문구"를 따른다

## 1. 화면 성격

화면을 만들기 전에 아래 표에서 화면 성격을 하나 고른다. 성격이 겹치면 화면의 주된 목적을 기준으로 고르고, 그래도 정할 수 없으면 사람에게 묻는다.

| 화면 성격 | 이런 화면 | 주된 목적 |
| --- | --- | --- |
| 홈 | 앱 첫 화면, 탭 첫 화면 | 여러 기능으로 들어가는 입구를 한눈에 본다 |
| 목록 | 피드, 내역, 장바구니, 알림 | 같은 형식의 항목을 훑어보고 하나를 고른다 |
| 검색 | 통합 검색, 주소 찾기 | 찾는 것을 입력하고 결과에서 고른다 |
| 상세 | 상품 상세, 글 보기, 프로필 | 한 대상을 자세히 보고 행동한다 |
| 입력 | 로그인, 회원가입, 글쓰기, 정보 수정 | 값을 넣어 제출한다 |
| 확인 | 주문서, 송금 확인, 신청 내용 확인 | 제출 직전에 넣은 내용을 한 번에 확인한다 |
| 결과 | 결제 결과, 송금 결과, 본인 인증 결과 | 이 화면에서 처리를 기다리고 결과를 확인한다 |
| 완료 안내 | 가입 완료, 탈퇴 완료, 신청 접수 완료 | 앞 화면에서 끝난 처리를 알리고 다음으로 보낸다 |
| 설정 | 알림 설정, 앱 설정 | 켜고 끄거나 값을 바꾸면 바로 반영된다 |
| 시작 | 앱 소개, 권한 안내, 첫 설정 | 처음 쓰는 사람이 바로 시작하게 한다 |
| 고정 내용 | 약관, 소개, 공지 본문 | 정해진 글을 읽는다 |
| 기타 | 지도, 채팅, 편집기(꾸미기), 카메라, 영상 | 위 성격 어디에도 맞지 않는다 |

- 결과와 완료 안내는 처리를 이 화면에서 기다리는지로 나눈다. 앞 화면에서 처리가 끝난 뒤 열리는 화면은 완료 안내다.
- 값을 고쳐 "저장하기"로 제출하는 화면은 설정이 아니라 입력이다
- 홈과 목록은 블록의 형식으로 나눈다. 같은 형식의 항목이 이어지면 목록, 요약 · 바로가기 · 추천처럼 성격이 다른 블록을 묶으면 홈이다.

### 1-1. 기타

- 기타는 성격이 겹칠 때가 아니라 어디에도 맞지 않을 때만 고른다
- 공통 구성(2-1)은 그대로 따른다
- 필요한 컴포넌트가 MVP 19개에 없으면 `AGENTS.md`의 "없는 UI는 묻고 임시로 만든다"를 따른다
- 상태 장면은 `docs/UX.md` "상태"의 만드는 조건으로 판단한다
- 구성 계획에 "기타(지도)"처럼 적고 사람에게 확인받는다. 같은 기타가 반복되면 화면 성격 추가를 요청한다.

## 2. 화면 성격별 구성

### 2-1. 모든 화면에 공통

| 자리 | 두는 것 | 기준 |
| --- | --- | --- |
| 맨 위 | Top bar: 화면 제목 + 첫 화면이 아니면 뒤로가기 또는 닫기 | 뒤로가기와 닫기 중 무엇을 쓸지는 `docs/UX.md` "뒤로가기와 닫기는 다르다" |
| Top bar 바로 아래(상단 이미지가 있으면 그 아래) | 지속 안내가 있을 때만 Banner 1개 | `DESIGN.md` "컴포넌트별 사용 규칙"의 Banner |
| 가운데 | 본문(화면 성격별로 2-2) | 중요한 것을 먼저, 위에 둔다(`docs/UX.md` "정보 구조") |
| 맨 아래 | 주요 행동이 있으면 하단 고정 버튼(`Button` `lg`) 1개 | 채움 버튼은 한 화면에 하나다(`DESIGN.md` "컴포넌트별 사용 규칙"의 Button) |

- `[권장]` Top bar 오른쪽에는 보조 행동을 2개까지 둔다. 더 많으면 더보기(5장)로 모은다.
- 하단 고정 버튼과 함께 보조 행동이 하나 있으면 같은 줄 왼쪽에 secondary로 나란히 둔다. 나란히 두는 버튼은 2개까지다(`docs/UX.md` "행동의 위계").

### 2-2. 화면 성격별 본문과 주요 행동

| 화면 성격 | 본문 (위에서 아래로) | 주요 행동 | 주로 쓰는 컴포넌트 |
| --- | --- | --- | --- |
| 홈 | 성격이 다른 블록(요약 · 바로가기 · 추천 등)을 중요한 순서로. 블록마다 다른 화면으로 이동한다 | 없다 | Card, List item, Tabs, Badge, Avatar |
| 목록 | 분류가 있으면 Tabs → 같은 형식의 항목 목록 | 새로 만드는 행동이 있을 때만 하단 고정 버튼 | List item, Card, Badge, Avatar, Tabs |
| 검색 | 검색 입력칸 → 분류가 있으면 Tabs → 결과 목록 | 없다. 결과 한 줄을 눌러 상세로 간다. | Input, Tabs, List item, Card |
| 상세 | 핵심 정보(이미지 · 이름 · 가격 등) → 설명 → 부가 정보 | 그 대상에 하는 가장 중요한 행동 1개를 하단 고정 버튼으로 | Card, Badge, Avatar, List item |
| 입력 | 필요하면 안내 한 줄 → 입력 항목. 항목 순서와 묶음은 `docs/UX.md` "구성" | 하단 고정 제출 버튼. 다 채우기 전에는 누를 수 없다(`docs/UX.md` "제출") | Input, Textarea, Select, Checkbox, Radio, Switch |
| 확인 | 넣은 내용 요약(항목 이름 + 값) → 항목마다 고치러 가는 길 | 하단 고정 제출 버튼 | List item, Card |
| 결과 | 결과를 말하는 제목 → 핵심 내용 요약(금액 · 받는 사람 · 상품 등) | 다음 행동 1개를 하단 고정 버튼으로 | List item, Card |
| 완료 안내 | 무엇이 끝났는지 말하는 제목 → 필요하면 다음에 일어날 일 한 줄 | 다음 행동 1개를 하단 고정 버튼으로 | Button |
| 설정 | 주제별로 묶은 List item. 한 줄에 Switch 또는 고른 값을 보여 주는 Select 하나 | 없다. 바꾸면 바로 반영되므로 저장 버튼을 두지 않는다. | List item, Switch, Select |
| 시작 | 한 화면에 안내 하나(제목 + 짧은 설명) | 다음으로 가는 하단 고정 버튼. Top bar 오른쪽에 건너뛰기 | Top bar, Button |
| 고정 내용 | 제목 → 본문 글 | 없다. 동의를 받는 화면이면 입력으로 본다. | — |
| 기타 | 2-1 공통 구성 안에서 화면에 맞게 정하고 사람에게 확인받는다 | 화면에 맞게 정한다 | 1-1을 따른다 |

- 결과 · 완료 안내 화면의 Top bar에는 뒤로가기 대신 닫기를 둔다. 끝난 과정에 뒤로가기로 다시 들어가지 않게 하기 위해서다(`docs/UX.md` "흐름").
- 확인 화면에서 돈이 오가면 `docs/UX.md` "의사결정과 신뢰"에서 정한 확인 항목(최종 금액 · 수수료 · 받는 사람 또는 상품 · 결제 수단)을 모두 둔다
- 시작 화면은 짧게 만들고 언제든 건너뛸 수 있게 한다. 기기 권한은 시작 화면에서 한꺼번에 묻지 않고, 그 기능을 쓰는 순간에 묻는다(`docs/UX.md` "의사결정과 신뢰"). 첫 설정에서 값을 넣어 제출하는 화면은 입력을 따른다.
- `[권장]` 목록 · 검색 결과의 한 줄은 앱 전체에서 같은 순서로 둔다: 왼쪽 이미지 또는 Avatar → 제목 → 보조 정보 → 오른쪽 상태(Badge) 또는 이동 표시
- `[권장]` 목록에서 사진이 주인 항목(상품 등)은 Card, 글이 주인 항목(알림 · 내역 등)은 List item으로 만든다

### 2-3. 여러 단계 흐름

- 여러 단계로 이어지는 흐름은 단계마다 그 단계의 화면 성격(주로 입력)을 따른다
- `[권장]` 본문 맨 위에 지금 단계와 전체 단계 수를 글자로 보여 준다(예: "2/4"). 진행 막대가 필요하면 0장의 없는 UI 규칙을 따른다(`docs/UX.md` "정보 구조").
- 단계 표시는 확인 · 결과 · 완료 안내를 뺀 단계에만 둔다. 전체 단계 수도 이 단계들만 센다.
- 단계 사이 이동과 입력값 유지는 `docs/UX.md` "뒤로가기와 닫기는 다르다"를 따른다
- 단계별 브리프 · 프로토타입 파일 이름은 `docs/CONVENTIONS.md` "코드·피그마"의 여러 단계 흐름 줄을 따른다
- 마지막은 확인 → 결과 또는 완료 안내로 끝낸다

## 3. 화면 성격별 상태 장면

화면 성격의 줄을 찾아 칸에 적힌 장면을 묶음마다 하나씩 만든다. "—"인 묶음은 만들지 않는다.

| 화면 성격 | 정상 | 기다림 | 비어 있음 | 실패 | 이용 불가 |
| --- | --- | --- | --- | --- | --- |
| 홈 | 블록이 채워진 모습 | 블록마다 불러오는 중 | 블록마다 아직 내용 없음 | 블록마다 불러오기 실패 | — |
| 목록 | 내용 있음 | 처음 불러오는 중 | 아직 내용 없음 | 불러오기 실패 | — |
| 검색 | 결과 있음 | 결과를 불러오는 중 | 검색 결과 없음 | 불러오기 실패 | — |
| 상세 | 내용 있음 | 불러오는 중 | — | 불러오기 실패 | 판매 종료 · 삭제됨 |
| 입력 | 입력칸과 제출 버튼. 다 채우기 전에는 누를 수 없다 | 제출 중 | — | 입력값 오류(제출한 뒤 알게 된 것 포함) 또는 제출 실패 | — |
| 확인 | 넣은 내용 요약과 제출 버튼 | 제출 중 | — | 제출 실패(결제 · 송금은 결과 화면의 실패 장면) | — |
| 결과 | 성공. 결과 + 다음 행동 | 처리 중, 처리 대기 | — | 실패. 이유 + 다시 시도 또는 돌아갈 길 | 한도 초과 · 시간 만료 |
| 완료 안내 | 끝난 내용 + 다음 행동 | — | — | — | — |
| 설정 | 저장된 현재 값 | 현재 값을 불러오는 중 | — | 저장 실패. 바꾸기 전 값으로 돌아가고 알린다 | — |
| 시작 | 안내 내용 | — | — | — | — |
| 고정 내용 | 내용 | — | — | — | — |

- 표에 없는 화면은 `docs/UX.md` "상태"의 만드는 조건으로 판단한다
- 완료 안내 화면에 실패 장면을 만들지 않는다. 처리 실패는 처리를 한 앞 화면(입력 · 확인 · 결과)의 실패 장면이다.
- 로그인이 필요한 화면은 성격과 상관없이 이용 불가(로그인 필요) 장면을 더한다
- 홈은 기다림 · 비어 있음 · 실패를 블록마다 따로 보여 주고 본문 전체를 바꾸지 않는다. 모든 블록이 실패했을 때만 본문 전체를 실패로 바꾼다.
- 결과 · 완료 안내의 정상 장면은 2-2의 구성을 따른다

## 4. 상태 화면 구성

### 4-1. 공통

- 상태 장면에서도 Top bar는 그대로 둔다. 바뀌는 것은 본문 자리다.
- 본문 자리 전체를 상태로 바꿀 때는 본문 자리 가운데에 위에서 아래로 제목 → 설명(선택) → 버튼 1개를 둔다
- 상태 화면의 버튼은 `Button` `md`로 만든다
- 같은 화면에 하단 고정 채움 버튼이 있으면 상태 화면의 버튼은 outline `md`(`button-outline-md`)로 만든다. 채움 버튼은 한 화면에 하나이고, 본문 가운데 버튼이 하단 고정 버튼만큼 크면 어색해서다. `DESIGN.md`에 `button-outline-md`가 추가되기 전까지는 만들기 전에 사람에게 묻는다.

### 4-2. 상태별 구성

| 상태 | 어디에 보여 주나 | 구성 |
| --- | --- | --- |
| 기다림 | 처리 중인 자리에만 | 어떤 표현을 쓸지는 `docs/UX.md` "로딩". Top bar · 하단 고정 버튼 · 이미 받은 내용은 그대로 둔다 |
| 비어 있음(아직 없음) | 목록이 들어갈 본문 자리 | 왜 비었는지 제목 + 채우는 첫 행동 버튼 |
| 비어 있음(검색 결과 없음) | 결과 목록 자리 | 검색 입력칸과 검색어는 그대로 두고, 결과 자리에 안내 + 조건을 바꾸거나 초기화하는 버튼 |
| 실패(입력값) | 문제가 생긴 입력칸 바로 아래 | 제자리 메시지(`docs/UX.md` "검사"). 비밀번호 틀림처럼 제출한 뒤 알게 된 입력값 오류도 여기에 보여 준다. 본문 전체를 바꾸지 않는다. |
| 실패(불러오기) | 불러오지 못한 본문 자리 | 무엇이 안 됐는지 제목 + "다시 시도" 버튼. 나가는 방법은 `docs/UX.md` "상태"의 실패 화면 표를 따른다 |
| 실패(제출 · 저장) | 화면은 그대로 두고 알림만 | 입력 내용을 지우지 않고 일시 알림(Toast)으로 알린다. 다시 제출은 원래 버튼으로 한다. 문구는 `docs/WRITING.md` "오류 문구"를 따른다. |
| 실패(결제 · 송금처럼 되돌릴 수 없는 제출) | 결과 화면 | 일시 알림으로 보여 주지 않고 결과 화면의 실패 장면(3장)으로 보여 준다. 사라지는 알림으로는 놓칠 수 있기 때문이다(`docs/UX.md` "피드백의 종류"). |
| 실패(인터넷 끊김) | Top bar 바로 아래(상단 이미지가 있으면 그 아래) | Banner(critical)로 알리고, 연결되면 사라진다 |
| 이용 불가(볼 수는 있음) | Top bar 바로 아래(상단 이미지가 있으면 그 아래) + 하단 고정 버튼 | 판매 종료 · 품절처럼 내용은 보여 줄 수 있으면 Banner(informative)로 이유를 알리고, 하단 고정 버튼을 다른 길(비슷한 상품 보기 등)로 바꾼다 |
| 이용 불가(볼 수 없음) | 본문 자리 전체 | 삭제됨 · 로그인 필요 · 권한 꺼짐처럼 내용을 보여 줄 수 없으면 이유 제목 + 다른 길 버튼(로그인하기 · 설정 열기 · 홈으로). 다시 시도 버튼은 두지 않는다 |

## 5. 더보기 목록

- Top bar 오른쪽 보조 행동이 많으면 중요한 것만 보이고 나머지는 더보기 아이콘 하나에 모은다(`docs/UX.md` "행동의 위계"). 몇 개까지 보일지는 2-1을 따른다.
- 더보기를 누르면 Bottom sheet로 행동 목록을 연다(`DESIGN.md` "피드백 종류별 컴포넌트"의 선택 목록)
- 목록은 List item 한 줄에 행동 하나를 둔다. 각 줄은 행동을 말하는 짧은 이름이다(`docs/WRITING.md` "버튼 · 링크 이름").
- 자주 쓰는 행동을 위에, 위험한 행동(삭제 · 신고 · 나가기)은 맨 아래에 둔다. 위험한 행동의 글자는 `fg.critical`로 구분하고, 글자 크기별 굵기는 `DESIGN.md` "Colors"를 따른다.
- 위험한 행동을 고르면 Bottom sheet를 닫고 확인 요청을 띄운다(`docs/UX.md` "위험한 행동")
- 닫는 방법은 `docs/UX.md` "피드백의 종류"의 선택 목록을 따른다

## Do's and Don'ts

`/ui-review`가 이 목록을 점검표로 쓴다. "(웹 프로토타입에서 확인 불가)" 표시가 있는 항목은 건너뛴다.

### 화면 성격과 구성

- [ ] 화면 성격이 1장 표의 하나로 정해져 있다
- [ ] 맨 위에 화면 제목이 있는 Top bar가 있고, 첫 화면이 아니면 뒤로가기 또는 닫기가 있다
- [ ] 결과 · 완료 안내 화면에는 뒤로가기 대신 닫기가 있다
- [ ] 설정 화면에 저장 버튼이 없고, 바꾼 값이 바로 반영된다
- [ ] 확인 화면의 항목마다 고치러 가는 길이 있다
- [ ] 시작 화면에 건너뛰기가 있고, 기기 권한을 한꺼번에 묻지 않는다
- [ ] `[권장]` 여러 단계 흐름에서 확인 · 결과 · 완료 안내를 뺀 화면은 본문 맨 위에 지금 단계와 전체 단계 수가 있다(예: "2/4")
- [ ] 확인 · 결과 · 완료 안내 화면에는 단계 표시가 없다

### 상태

- [ ] 3장 표에서 화면 성격에 맞는 상태 장면이 모두 있고, "—"인 장면은 만들지 않았다
- [ ] 상태 장면에서도 Top bar가 그대로 있다
- [ ] 하단 고정 채움 버튼이 있는 화면의 상태 장면 버튼은 채움이 아니라 outline이다
- [ ] 홈의 상태는 블록마다 따로 보이고, 모든 블록이 실패할 때만 본문 전체가 실패로 바뀐다
- [ ] 검색 결과 없음 장면에 검색어가 그대로 보인다
- [ ] 입력값 실패는 제출한 뒤 알게 된 것도 입력칸 아래에 보이고, 본문 전체를 바꾸지 않는다
- [ ] 제출 · 저장 실패 후에도 입력한 내용이 그대로 있다
- [ ] 결제 · 송금 실패를 일시 알림으로만 보여 주지 않는다
- [ ] 이용 불가 장면에 다시 시도 버튼이 없고 다른 길 버튼이 있다
- [ ] 완료 안내 화면에 실패 장면이 없다

### 더보기

- [ ] 더보기 목록은 Bottom sheet이고, 위험한 행동이 맨 아래에 `fg.critical` 글자로 있다
