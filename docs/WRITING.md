> 상태: 초안 v0.2 · 태스크: 1-4
> 이 문서는 화면에 들어가는 **문장**(말투 · 버튼 이름 · 오류 · 안내 · 숫자 형식)을 정한다
> 언제 · 어디에 보여 줄지는 `docs/UX.md`, 색 · 크기 · 컴포넌트 모양은 `DESIGN.md`, 화면 유형별 구성은 `docs/PATTERNS.md`를 따른다

## 0. 읽는 법

- 표시(표시 없음 · `[권장]` · `[결정 필요]` · (웹 프로토타입에서 확인 불가))의 뜻과 AI 행동은 `docs/CONVENTIONS.md` "MD 작성"을 따른다
- 따를 기준은 토스 TDS와 당근 SEED의 라이팅 규칙이다. 규칙만 참고하고 문장은 새로 쓴다. 다른 서비스의 문구를 그대로 옮기지 않는다.
- 이 문서의 화면 문구 예시는 따옴표로 감싼다. 예시는 규칙을 보여 주려고 새로 쓴 문장이다.

## 1. 말투

### 1-1. 기본: "~해요"

- 화면 문구는 "~해요"로 쓴다(예: "저장했어요", "다시 시도해 주세요")
- 친구에게 말하듯 친근하게 쓰되, 반말 · 유행어 · 은어는 쓰지 않는다
- 높임은 꼭 필요할 때만 쓴다. "~하실 수 있어요" 대신 "~할 수 있어요"로 쓴다. 높임이 겹치면 문장이 길어지고 딱딱해진다.
- 잘못이 우리 쪽에 있는 오류에도 "~해요"를 쓴다. 말투를 바꾸면 사과가 아니라 거리감으로 느껴진다.

### 1-2. 정확해야 하는 화면(엄격한 화면): "~합니다"

말을 잘못 쓰면 법적 · 금전적 책임이 생기는 문장이 화면의 중심인 경우 "~합니다"로 쓴다. 기능이 위험한지가 아니라 **문장 자체가 약속이 되는지**로 판단한다.

| 해당한다 ("~합니다") | 해당하지 않는다 ("~해요") |
| --- | --- |
| 이용약관 · 개인정보 처리방침 본문 | 결제하기 버튼이 있는 일반 결제 화면 |
| 약관 · 개인정보 수집 · 마케팅 수신 동의 화면 | 송금 · 탈퇴처럼 되돌릴 수 없는 행동의 확인 요청 |
| 결제 · 환불 · 해지 조건 고지문의 전문 | 결제 화면 안의 짧은 조건 고지(예: 정기 결제 안내) |
| | 결제 완료 · 송금 완료 결과 화면 |
| 청약 철회처럼 법으로 알려야 하는 안내 | 오류 · 빈 화면 · 로딩 안내 |

- 되돌릴 수 없는 행동은 말투가 아니라 확인 요청으로 다룬다(`docs/UX.md` "위험한 행동")
- "~합니다" 화면도 버튼 이름은 행동을 말하는 짧은 말로 쓴다(예: "동의하기")
- 한 화면 안에서 두 말투를 섞지 않는다. 일반 화면 안에 들어가는 약관 요약 · 결제 조건 고지는 "~해요"로 쓰고, 전문은 "~합니다" 화면으로 연결한다.
- 브리프의 `strict` 값은 이 표로 정한다(`docs/BRIEF.md`)

## 2. 문장 기본

| 규칙 | 이유 |
| --- | --- |
| 다음에 무슨 일이 일어날지 미리 알려 준다 | 결과를 모르면 누르기 불안하다 |
| 뜻을 바꾸지 않는 말은 뺀다("~하는 것을", "해당", "진행") | 사용자는 읽지 않고 훑어본다 |
| 지금 필요한 정보 하나에 집중한다. 한 문장에는 한 가지만 말한다. | 설명이 많으면 핵심을 놓친다 |
| 소리 내 읽었을 때 자연스러운 쉬운 말로 쓴다. 한자어 · 전문 용어 · 기능 이름 · 줄임말을 쓰지 않는다. | 따로 배우지 않아도 이해돼야 한다 |
| 하는 사람(사용자)을 주어로, 능동형으로 쓴다("후기를 보냈어요") | 누가 무엇을 했는지 바로 보인다 |
| 할 수 없는 것보다 할 수 있는 것을 말한다. 이중 부정을 쓰지 않는다. | 다음 행동이 보인다 |
| 권하고 강요하지 않는다. 겁을 주거나 서두르게 하지 않는다. | 사용자가 스스로 고른다고 느껴야 한다(`docs/UX.md` "의사결정과 신뢰") |
| 누구나 아는 말만 쓴다. 유행어 · 은어 · 밈을 쓰지 않는다. | 나이 · 배경에 따라 이해가 달라진다 |
| 결과 뒤에 있는 감정을 생각한다. 실패 · 거절 순간에는 탓하지 않고 다음 방법을 준다. | 신뢰가 쌓인다 |

예시

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| "해당 게시글의 삭제가 완료되었습니다" | "게시글을 삭제했어요" |
| "실패하지 않았어요" | "저장했어요" |
| "알 수 없는 오류(500)" | "잠시 후 다시 시도해 주세요" |

## 3. 표기

### 3-1. 마침표 · 문장부호

- 제목 · 버튼 · 항목 이름 · 탭 · 배지 · 메뉴에는 마침표를 찍지 않는다
- 본문 문장은 한 문장이면 마침표를 찍지 않고, 두 문장 이상이면 마지막 문장까지 모두 찍는다
- 느낌표는 축하처럼 감정을 꼭 전해야 할 때만 한 번 쓴다 `[권장]`
- 이모지는 화면 문구에 쓰지 않는다
- 따옴표는 큰따옴표(" ")만 쓴다

### 3-2. 띄어쓰기 · 용어

- 같은 대상은 앱 전체에서 같은 이름으로 부른다(`docs/UX.md` "이해하는 데 어려움이 있는 사용자")
- 상태 이름은 붙여 쓰고(예: "예약중" 배지), 문장 안의 같은 말은 띄어 쓴다(예: "예약 중인 상품이에요")
- 외래어는 굳어진 말만 쓰고, 우리말이 있으면 우리말을 쓴다(예: "업로드" 대신 "올리기"가 자연스러우면 "올리기")

### 3-3. 숫자 · 날짜 · 시간 · 금액

| 대상 | 형식 | 예시 |
| --- | --- | --- |
| 숫자 | 아라비아 숫자. 네 자리부터 쉼표 | "3개", "1,200명" |
| 금액 | 숫자 + "원", 쉼표 | "12,000원" |
| 큰 금액 | `[권장]` 만 · 억 단위를 섞어 읽기 쉽게 | "1억 2,000만 원" |
| 단위 | 숫자와 붙여 쓴다 | "5분", "30%" |
| 날짜 | 기본은 올해면 "11월 13일", 다른 해면 "2026년 11월 13일"이다. 요일이 필요하면 "11월 13일 (금)"으로 쓴다. 목록 · 카드처럼 좁은 자리는 요약형 "2026.11.13"을 쓴다. | "11월 13일" · "2026.11.13" |
| 시간 | 기본은 "오후 3시 5분"(정각이면 "오후 3시")이다. 좁은 자리는 요약형 "오후 3:05"를 쓴다. | "오후 3시 5분" · "오후 3:05" |
| 지난 시간 | 1분 미만 "방금", 1시간 미만 "N분 전", 오늘 "N시간 전", 어제 "어제", 그 전은 날짜 | "3시간 전" |
| 전화번호 | 하이픈으로 나눈다 | "010-1234-5678" |

- 한 앱 안에서 같은 대상은 같은 형식으로 보여 준다
- 금액 · 수수료는 줄이거나 반올림하지 않고 정확한 값을 보여 준다(`docs/UX.md` "의사결정과 신뢰")

## 4. 버튼 · 링크 이름

- 누르면 생기는 결과를 동사로 말한다(예: "저장하기", "삭제하기", "주문하기"). "확인" · "예" · "다음"만으로 쓰지 않는다.
- 2~6글자의 짧은 말로 쓴다. 길어지면 대상을 빼고 행동만 남긴다(예: "게시글 삭제하기" → "삭제하기").
- 같은 행동은 앱 전체에서 같은 이름을 쓴다
- 두 버튼을 나란히 둘 때는 서로 다른 결과가 보이게 쓴다. 취소 쪽은 기본 "취소"로 쓰고, 창만 닫는 안내는 "닫기"로 쓴다. 남는 쪽의 결과가 분명하면 그 결과를 쓴다(예: 작성 중 나가기 확인의 "나가기" · "계속 쓰기").
- 링크는 이동할 곳을 말한다(예: "비밀번호 찾기"). "여기를 누르세요"처럼 쓰지 않는다.
- 제출 버튼 이름은 `docs/UX.md` "제출"의 기준(결과를 말한다)을 따른다

## 5. 항목 이름 · 안내 글자 · 도움말

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 항목 이름 | 짧은 명사로 쓴다. 물음표 · 마침표를 쓰지 않는다. | "휴대폰 번호" |
| 안내 글자(입력칸 안) | 입력 예시만 쓴다. 설명 · 조건을 쓰지 않는다. | "010-1234-5678" |
| 도움말(입력칸 아래) | 조건을 한 문장으로 미리 알린다 | "8자 이상, 숫자를 섞어 주세요" |
| 선택 표시 | 항목 이름 뒤에 붙인다 | "추천인 코드 (선택)" |

- 언제 보여 줄지 · 필수 표시 방식은 `docs/UX.md` "항목 이름과 안내"를 따른다

## 6. 오류 문구

오류 문구의 역할은 사용자가 다음 단계로 넘어가게 돕는 것이다

- 무슨 일인지 → 왜인지(알 수 있으면) → 어떻게 하면 되는지 순서로 쓴다. 해결 방법이 없으면 기다리면 되는지, 어디에 물으면 되는지를 쓴다.
- 사용자 탓으로 쓰지 않는다. "잘못 입력했어요" 대신 무엇을 넣으면 되는지 쓴다.
- 오류 코드 · 서버 용어 · "알 수 없는 오류"를 보여 주지 않는다
- 입력칸 오류는 한 문장으로 쓴다

| 상황 | 쓰지 않는다 | 쓴다 |
| --- | --- | --- |
| 형식이 다름 | "올바르지 않은 형식입니다" | "이메일 주소를 다시 확인해 주세요" |
| 조건 미달 | "비밀번호 오류" | "8자 이상 입력해 주세요" |
| 연결 끊김 | "네트워크 에러" | "인터넷 연결을 확인하고 다시 시도해 주세요" |
| 서버 문제 | "Error 503" | "잠시 문제가 생겼어요. 조금 뒤에 다시 시도해 주세요." |

- 어디에 · 언제 보여 줄지는 `docs/UX.md` "오류가 났을 때" · "검사"를 따른다

## 7. 확인 요청 문구

| 부분 | 규칙 | 예시 |
| --- | --- | --- |
| 제목 | 무엇을 할지 묻는 한 문장. "정말"을 쓰지 않는다. | "게시글을 삭제할까요?" |
| 설명 | 무엇이 바뀌는지, 되돌릴 수 있는지를 쓴다. 비워 두지 않는다. | "삭제한 글은 다시 볼 수 없어요" |
| 실행 버튼 | 제목의 행동을 그대로 쓴다 | "삭제하기" |
| 취소 버튼 | 기본 "취소". 남는 쪽의 결과가 분명하면 그 결과를 쓴다(4장). | "취소" · "계속 쓰기" |

- 되돌릴 수 없고 영향이 크면 사라지는 것을 구체적으로 쓴다(예: "채팅 32개와 거래 후기가 모두 지워져요")
- 언제 띄울지 · 선택지 수는 `docs/UX.md` "피드백의 종류" · "위험한 행동"을 따른다

## 8. 일시 알림 · 지속 안내 문구

### 8-1. 일시 알림(Toast)

- 방금 일어난 결과를 한 문장으로 쓴다. 결과를 앞에 둔다(예: "링크를 복사했어요").
- 긍정형으로 쓴다(예: "올리기를 마쳤어요")
- 행동 버튼은 1~2단어의 구체적인 행동으로 쓴다(예: "되돌리기", "보러 가기")
- 결정이 필요한 내용은 쓰지 않는다(`docs/UX.md` "일시 알림")

### 8-2. 지속 안내(Banner)

- 지금 상태 + 할 일을 쓴다(예: "결제 수단이 만료됐어요. 새 카드를 등록해 주세요.")
- 제목을 쓸 때는 상태를 나타내는 짧은 말로 쓰고, 본문에서 제목을 되풀이하지 않는다(`DESIGN.md` "컴포넌트별 사용 규칙")

## 9. 상태별 문구

상태 이름과 언제 보여 줄지는 `docs/UX.md` "상태"를 따른다

### 9-1. 기다림

- 4초가 넘는 로딩에는 지금 하는 일을 한 문장으로 쓴다(예: "사진을 올리고 있어요")
- 진행 정도를 알 수 있는 긴 작업(파일 올리기 등)이 10초가 넘으면 남은 시간이나 진행 정도를 함께 쓴다(예: "1분 정도 걸려요")
- 진행 정도를 알 수 없는 요청이 10초 안에 끝나지 않으면 `docs/UX.md` "로딩"대로 실패로 바꾸고, 문구는 6장을 따른다
- "잠시만 기다려 주세요"만 쓰지 않는다. 무엇을 기다리는지 쓴다.

### 9-2. 비어 있음

- 왜 비어 있는지 + 다음 행동을 쓴다(예: "아직 받은 알림이 없어요" + 버튼 "알림 설정하기")
- 사용자를 탓하거나 아쉬워하는 말("아무것도 없네요 😢")을 쓰지 않는다
- 검색 결과가 없으면 검색어를 보여 주고 다른 방법을 권한다(예: `"운동화" 검색 결과가 없어요. 다른 단어로 찾아보세요.`)
- 빈 화면 구성은 `docs/PATTERNS.md`를 따른다

### 9-3. 실패

- 오류 문구(6장)를 따른다

### 9-4. 이용 불가

- 이유 + 다른 길을 쓴다. 다시 시도는 권하지 않는다(예: "판매가 끝난 상품이에요" + 버튼 "비슷한 상품 보기").
- 로그인 · 권한이 필요하면 무엇을 하면 되는지 쓴다(예: "로그인하면 찜한 상품을 볼 수 있어요" + 버튼 "로그인하기")

### 9-5. 완료

- 무엇이 끝났는지와 다음에 일어날 일을 쓴다(예: "주문을 마쳤어요. 내일 도착해요.")

## 10. 권한 요청 문구

- 권한을 묻기 전에 우리 화면에서 이유를 먼저 한 문장으로 쓴다(예: "가까운 매장을 찾으려면 위치 권한이 필요해요")
- 이유는 사용자가 얻는 것을 말한다. "서비스 이용을 위해" 같은 말로 쓰지 않는다.
- 거절한 뒤에는 다시 켜는 방법을 쓴다(예: "설정 > 위치에서 다시 켤 수 있어요")
- 언제 물을지는 `docs/UX.md` "의사결정과 신뢰"를 따른다

## Do's and Don'ts

`/ui-review`가 이 목록을 점검표로 쓴다. "(웹 프로토타입에서 확인 불가)" 표시가 있는 항목은 건너뛴다.

### 말투

- [ ] 화면 문구는 "~해요"로 쓴다. 1-2 표에 해당하는 화면만 "~합니다"로 쓴다.
- [ ] 한 화면 안에서 "~해요"와 "~합니다"를 섞지 않는다. 일반 화면 안의 약관 요약 · 결제 조건 고지는 "~해요"로 쓴다.
- [ ] "~하실 수 있어요"처럼 높임을 겹쳐 쓰지 않는다
- [ ] 반말 · 유행어 · 은어 · 이모지를 쓰지 않는다

### 문장

- [ ] 한 문장에는 한 가지만 말한다
- [ ] 한자어 · 전문 용어 · 기능 이름 · 줄임말 대신 쉬운 말을 쓴다
- [ ] 이중 부정을 쓰지 않는다
- [ ] 제목 · 버튼 · 항목 이름 · 탭 · 배지에 마침표를 찍지 않는다
- [ ] 본문이 두 문장 이상이면 모든 문장 끝에 마침표를 찍는다

### 버튼

- [ ] 버튼 이름은 결과를 말하는 동사다. "확인" · "예" 하나만 쓰지 않는다.
- [ ] 같은 행동은 앱 전체에서 같은 버튼 이름을 쓴다
- [ ] 확인 요청의 실행 버튼은 제목의 행동과 같은 말이다

### 오류 · 안내

- [ ] 오류 문구에 어떻게 하면 되는지가 들어 있다
- [ ] 오류 코드 · 서버 용어 · "알 수 없는 오류"를 보여 주지 않는다
- [ ] 오류 문구가 사용자 탓으로 읽히지 않는다
- [ ] 확인 요청에 설명이 있고, 제목은 "~할까요?"로 묻는다
- [ ] 일시 알림은 한 문장이고 결과를 먼저 말한다
- [ ] 빈 화면에 비어 있는 이유와 다음 행동이 있다
- [ ] 4초 넘는 로딩 안내는 무엇을 기다리는지 말한다
- [ ] 이용 불가 문구에 이유와 다른 길이 있고, 다시 시도를 권하지 않는다
- [ ] 권한을 묻기 전에 사용자가 얻는 이유를 먼저 보여 준다 (웹 프로토타입에서 확인 불가)

### 숫자 · 표기

- [ ] 금액은 쉼표와 "원"을 붙인 숫자로 쓴다("12,000원")
- [ ] 같은 대상의 날짜 · 시간 형식이 앱 전체에서 같다
- [ ] 입력칸 안 안내 글자는 입력 예시만 담는다
